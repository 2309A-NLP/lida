# 性能分析 - 当前瓶颈报告

## 1. 启动耗时分析

### 当前状态
- 服务启动时间：约 2-3 秒
- 由于禁用了 BGE 本地嵌入模型加载（USE_LOCAL_EMBEDDING=false），启动速度较快
- 若启用本地嵌入模型，启动时间预计增加 10-30 秒（模型加载 + 初始化）

### 瓶颈点
- FastAPI 应用初始化阶段需加载所有路由和中间件
- 知识库初始化时需扫描文件系统加载文档
- 未启用连接池，每次数据库操作创建新连接

## 2. 检索效率分析

### 当前检索方案
- 方案：jieba 分词 + BM25 关键词匹配
- 优点：无需依赖第三方模型或向量数据库，启动快，资源占用低
- 缺点：语义理解能力有限，同义词/近义词匹配效果差

### 检索延迟（预估）
- 小规模知识库（<100 文档）：< 50ms
- 中等规模知识库（100-1000 文档）：50-200ms
- 大规模知识库（>1000 文档）：200ms-1s

### 准确率瓶颈
- BM25 基于词频统计，无法理解上下文语义
- 用户提问与知识库文档用词不匹配时召回率低
- 无向量检索，无法利用 embedding 的语义相似度

## 3. API 调用延迟分析

### DeepSeek API
- 单次请求延迟：500ms - 3s（取决于模型和请求长度）
- 当前模式：非流式响应，需等待完整回复返回
- 用户感知延迟 = API 延迟 + 检索延迟 + 处理开销

### 网络延迟
- 从 WSL 环境调用 DeepSeek API 存在额外网络跳转
- 建议使用代理或直连以降低延迟

## 4. 内存与 CPU 使用

### 当前状态
- 内存使用：约 100-200MB（未加载本地模型）
- CPU 使用：低（主要瓶颈在 API 调用等待，非计算密集型）

### 若启用本地嵌入模型
- 内存使用预计增加 500MB - 2GB（取决于模型大小）
- CPU/GPU 使用将显著增加

## 5. 总结

| 维度 | 当前表现 | 优化空间 |
|------|---------|---------|
| 启动速度 | 快（2-3s） | 小 |
| 检索速度 | 快（<200ms） | 中等 |
| 检索准确率 | 低 | 大（建议向量检索） |
| API 响应 | 中（500ms-3s） | 大（流式响应） |
| 资源占用 | 低 | 小 |
