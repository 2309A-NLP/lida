## 一、LLM调优

### 1.1 推理模型参数优化

**问题**: MiMo-v2.5-pro 是推理模型，reasoning_tokens 先于 content_tokens 消耗预算。  
**症状**: 返回 content 为空字符串，`finish_reason='length'`。  
**优化**: `max_tokens=2000`（原为500），确保 reasoning 后有足够 token 输出。

```python
# 优化前
response = client.chat.completions.create(
    model="mimo-v2.5-pro",
    max_tokens=500  # 全部被reasoning吃掉，content为空
)

# 优化后
response = client.chat.completions.create(
    model="mimo-v2.5-pro",
    max_tokens=2000  # 预留足够空间给content
)
```

### 1.2 低温度保证结构化输出

`temperature=0.1`：降低随机性，保证LLM始终返回严格的JSON格式，避免解析失败。

### 1.3 JSON解析兼容性

LLM有时会在JSON外套`markdown代码块`，优化解析逻辑：

```python
# 优化前
content = response.choices[0].message.content.strip()
parsed = json.loads(content)  # 如果有```json包裹会报错

# 优化后
json_match = re.search(r'\{[\s\S]*\}', content)
if json_match:
    return json.loads(json_match.group())
return json.loads(content)
```

## 二、数据库优化

### 2.1 索引优化

4个索引覆盖所有查询场景：

| 索引 | 查询场景 |
|------|----------|
| `idx_date` | 日期范围查询（最常用） |
| `idx_member` | 按成员查询 |
| `idx_category` | 按类别查询 |
| `idx_type` | 收支类型筛选 |

### 2.2 SQLite线程安全

**问题**: Flask debug模式下多线程导致 `SQLite objects created in a thread can only be used in that same thread`。  
**优化**: 

```python
# database.py
conn = sqlite3.connect(db_path, check_same_thread=False)

# api.py
app.run(host='0.0.0.0', port=5000, debug=False)  # 禁用debug模式
```

### 2.3 单例模式

使用全局 `_db_instance` 单例避免重复创建数据库连接，减少资源开销。

## 三、删除功能模糊匹配优化

**问题**: 用户说"删除旅游团费用"，实际DB存的是"旅游团"。LLM提取的item和DB不完全匹配。  
**优化**: 多层回退搜索策略

```python
# 第1层：精确搜索
records = db.query_by_item(search_term)

# 第2层：去掉常见后缀重试
if not records:
    for suffix in ["费用", "记录", "的钱", "的费用", "花的"]:
        if search_term.endswith(suffix):
            shorter = search_term[:-len(suffix)]
            records = db.query_by_item(shorter)
            if records: break

# 第3层：去掉成员前缀重试
if not records and item:
    for prefix in ["女儿", "妈妈", "爸爸", "老妈", "老爸", "闺女"]:
        if item.startswith(prefix):
            shorter = item[len(prefix):]
            records = db.query_by_item(shorter)
            if records: break
```

## 四、默认值优化

减少用户输入负担，自动补全缺失字段：

| 字段 | 默认值策略 | 说明 |
|------|-----------|------|
| **date** | 当天日期 | 用户没说日期就默认今天 |
| **member** | "我" | 用户没指定成员就默认自己 |
| **item** | category内容 | item为空时用category代替 |
| **category** | "其他" | 未识别类别时兜底 |

## 六、容错与健壮性

### 6.1 LLM调用失败兜底

```python
try:
    response = client.chat.completions.create(...)
except Exception as e:
    print(f"LLM调用失败: {e}")
    return {"intent": "chat", "reply": "抱歉，我暂时无法理解您的输入，请重试。"}
```

### 6.2 JSON解析容错

- 正则提取 `{...}` 内容（兼容markdown代码块包裹）
- 单条/多条记录格式兼容（`records` 数组 + 字段级回退）

### 6.3 数据库异常处理

```python
try:
    record_id = db.add_record(...)
    return jsonify({"success": True, "id": record_id})
except Exception as e:
    return jsonify({"success": False, "error": str(e)})
```

所有API端点都有 try/except 包裹。

## 七、多记录支持优化

### 7.1 问题

原始设计只支持单条记账，用户说"买了奔驰300000，又买了衣服1000"时只识别了第一条。

### 7.2 优化

系统提示词增加多记录拆分规则，后端 `handle_record` 迭代 `records` 数组：

```python
# 单条确认
if len(valid_records) == 1:
    confirm_msg = "📋 请确认记录信息：\n• 日期：{date}\n..."

# 多条确认
else:
    confirm_msg = f"📋 共识别到 {len(valid_records)} 条记录，请确认：\n"
    for i, rec in enumerate(valid_records, 1):
        confirm_msg += f"【{i}】{rec['member']}，{rec['category']}，{rec['item']}，{type_str}{amount}元\n"
    confirm_msg += '\n确认全部记录请回复"确认"'
```

### 7.3 缓存结构兼容

`pending_confirmations["last"]` 同时兼容：
- 旧单条格式：`{"date": ..., "member": ...}`
- 新多条格式：`{"records": [{...}, {...}]}`
